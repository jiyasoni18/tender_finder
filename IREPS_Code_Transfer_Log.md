# IREPS Code Transfer & Integration Log

## Overview
This document explains the steps taken to transfer the working IREPS processing code from the `document web` project into the `tender_finder` project. The goal was to ensure that when a user selects **IREPS** (or any non-GeM portal) in the `tender_finder` Document Processing Workflow, it uses the exact same pipeline and code that is working correctly in the `document web` project.

## Steps Taken

### 1. Integrating Core Application Logic
The entire core processing folder from `document web` (`app`) has been natively integrated into our `tender_finder` backend environment following a standard FastAPI pattern. 
- **Source:** `C:\Users\DELL\Desktop\document web\tender-system\app`
- **Destination:** `c:\Users\DELL\Downloads\tender_finder\tender_finder\backend\app\services`

*(Note: We specifically moved the `intake` and `catalog` logic into an `app/services` structure to avoid colliding with unused routes, static files, and templates from the original standalone server, ensuring a clean monolithic integration into `tender_finder`.)*

This includes critical files like:
- `intake.py`: Orchestrates the requirement mapping and filling.
- `pdf_parser.py`: Extracts requirements directly from the NIT PDF.
- `excel_parser.py`: Generates the mapping Excel sheets.
- `ai_mapper.py` / `mapper.py`: Resolves requirements using local `.yaml` catalogs.

### 2. Copying the Template Documents
The `process_requirements()` script needs access to the base company documents (templates, letterheads, declarations) to successfully fill them out.
- **Source:** `C:\Users\DELL\Desktop\document web\documents railway`
- **Destination:** `c:\Users\DELL\Downloads\tender_finder\tender_finder\backend\documents railway`

### 3. Integrating with the Backend (`server.py`)
In the `tender_finder` backend API (`backend/server.py`), the `/api/docs/map` endpoint was modified to include an explicit branch for non-GeM (IREPS) websites. 

When the user selects IREPS:
1. **Bypass LLM Mapping:** We intercept the request and completely skip the massive GeM prompt.
2. **Execute Copied Logic:** 
   - We parse the NIT PDF using `parse_nit_pdf()` (from the copied `document web` code).
   - We extract all requirements, including automatically injecting the compulsory requirements (e.g., `certificate to be submitted`, `power of attorney`).
   - We construct the requirement Excel using `create_excel_from_requirements()`.
   - We execute `process_requirements()` which maps the requirements via the local `requirements_ireps.yaml` catalog and injects data (like `tender_no`, `company_name`) directly into the `.docx` files.
3. **Zip and Serve:** Once the documents are generated by `process_requirements()`, the endpoint zips the output directory and returns the URL directly to the frontend, allowing the user to download the final compiled package in a single step.

## Conclusion
The `tender_finder` application now successfully leverages the exact same logic and file parsing mechanisms for IREPS as the `document web` project, while keeping the GeM multi-step workflow completely separate and intact.
